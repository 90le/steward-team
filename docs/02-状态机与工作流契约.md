# 状态机与工作流契约（全生命周期）

> 状态唯一事实源 = GitHub label（需求池 90le/octo-server-demand-pool + 开发仓 90le/steward-team 的 issue/PR）。
> 每个阶段：Owner（谁执行）/ 输入 / 输出 / **DoD（机器可验证的完成定义）** / stop_after（到此为止，不等后续）。

## 全生命周期

```
[需求侧·已有] triage → claimed → prd-drafting → in-review
     ├─ 打回 → revise → 逐条修订 → in-review
     └─ 通过 → approved（小助标注 simple/complex）
[开发侧·新增] approved → (complex: 小衡架构评审) → dev-claimed(小码) → in-dev → code-review(小助)
     ├─ 代码打回 → in-dev → 逐条修订 → code-review
     └─ 代码通过 → qa(小检独立复跑) → 发布门(小衡清单+scar核验) → landed 候选 → 人类合并
任何阶段 → blocked-human（转人工，@考生+卡点，停原地）
```

## 阶段契约表

| # | 阶段 | Owner | 输入 | 输出 | DoD（全部满足才算完成） |
|---|------|-------|------|------|------------------------|
| 1 | triage | 小丘 | 用户诉求 | issue + type/priority/status 标签 | 标签齐；正文含用户原话；cron 运行记录在案 |
| 2 | prd-drafting→in-review | 小助 | approved 候选单 | PRD 评论（vN） | 模板全节；只 What 不 How；验收标准用户可感知；修订记录表 |
| 3 | approved | 小助 | review 通过 | label + 群播报 | 评审评论引用 PRD 具体条目；无未决开放问题（或已列拍板项） |
| 4 | dev-claimed→in-dev | 小码 | approved 单 | 开发仓分支 + 实现 | 分支名 `dev-<issue#>-<slug>`；小步提交；不碰需求池/考试工程 |
| 5 | code-review | 小助 | PR + DoD 证据 | 逐条评审评论 | 每条意见引用具体文件行号；通过/打回必须二选一明说 |
| 6 | qa | 小检 | review 通过的 PR | QA 报告（收尾模板） | 验收标准逐条亲跑复验；结论标注证据四档；只有 runtime_live_pass 支撑通过；skipped 如实标注 |
| 6.5 | 架构评审（触发式，complex 单在 dev-claimed 前） | 小衡 | 需求单 + 代码结构 | 技术方案意见 | 约束清单+取舍+风险，引用现有代码依据；simple 单跳过并留痕 |
| 7 | 发布门 | 小衡 | qa 通过的 PR | 发布纪要 | DoD 证据齐/分级达标、scar 已回写（无回归测试不收）、影响面与回滚方式明确 |
| 8 | landed | 人类 owner | 发布纪要 | merge | **只有人类执行**；Agent 终点=「PR 就绪待合并 @考生」 |

## 转移纪律

- 每次 label 流转必须附一句群播报（谁、从什么到什么、链接）——**状态转移无播报=没发生**。
- DoD 不满足就停留原地并在群里说卡点；禁止「先流转再补证据」。
- 同一单在同一阶段卡 3 轮（cron 周期）→ 强制转人工。
- 超出角色写权限的动作（合并/删库/改配置）→ 门禁四，转人工。

## 与现有机制的关系

- 需求侧阶段 1-3 由现有 cron（扫描 057815de / PM 3b87dffb）承载，**规则不破坏考试工程**：新增阶段只增量扩展 PM prompt 的「approved 之后转交」一步。
- 开发侧阶段 4-7 由小码的新 cron（扫开发仓 PR 状态）承载；代码打回/qa 证据由脚本预检（机械）+ 模型评审（表达）。
